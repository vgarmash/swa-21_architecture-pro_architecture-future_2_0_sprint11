# Обоснование событийного подхода для «Будущее 2.0»

## Введение

В данном документе представлено обоснование перехода от текущей интеграционной архитектуры (Apache Camel ESB + DWH) к событийно-ориентированной архитектуре (Event-Driven Architecture, EDA) на базе Apache Kafka.

---

## Анализ текущей ситуации

### Текущая архитектура

Компания «Будущее 2.0» использует следующую интеграционную архитектуру:

| Компонент | Технология | Назначение |
|----------|------------|------------|
| Хранилище данных | SQL Server 2008 DWH | Централизованное хранение всех данных |
| Интеграция | Apache Camel ESB | Маршрутизация и трансформация сообщений |
| Интерфейс | PowerBuilder | UI для операторов клиник |
| BI | Power BI | Аналитическая отчётность |

### Проблемы текущей архитектуры

1. **Высокая связанность (Tight Coupling):**
   - Все системы зависят от центрального DWH
   - Изменение в одной системе требует изменений во всех связанных
   - Невозможность независимого развития доменов

2. **Производительность:**
   - Формирование сложных отчётов занимает часы
   - Сотни терабайт данных с множеством трансформаций
   - BATCH-обработка не соответствует современным требованиям

3. **Time-to-Market:**
   - Медленное развёртывание новых функций
   - Необходимость согласования изменений между командами
   - Зависимость от команды DWH для любых изменений

4. **Масштабируемость:**
   - Вертикальное масштабирование DWH имеет пределы
   - Невозможность горизонтального масштабирования нагрузки
   - Ограниченная пропускная способность Camel при пиковых нагрузках

5. **Гибкость:**
   - Сложность добавления новых бизнес-направлений
   - Необходимость внесения бизнес-логики в DWH
   - Жёсткая схема данных, сложность изменений

---

## Преимущества событийного подхода

### 1. Гибкость (Flexibility)

**Проблема в текущей архитектуре:**
Добавление нового бизнес-направления (например, фармацевтической компании) требует значительных изменений в DWH и создания новых интеграционных маршрутов в Camel.

**Как событийный подход решает проблему:**

| Аспект | Решение |
|--------|---------|
| Добавление нового домена | Новый сервис просто подписывается на нужные топики |
| Изменение бизнес-логики | Каждый домен владеет своей локальной копией данных |
| Расширение данных | JSON-схемы позволяют добавлять поля без breaking changes |
| Удаление зависимостей | ACL (Anti-Corruption Layer) изолирует домены от легаси |

**Пример:**

> // Добавление фармацевтического домена
> // Не требует изменения DWH или других сервисов!
>
> 1. Создаётся новый топик: pharma.orders
> 2. Лечебный домен публикует TreatmentPrescribed
> 3. Фармацевтический домен подписывается и создаёт заказ на лекарства


### 2. Масштабируемость (Scalability)

**Проблема в текущей архитектуре:**
При пиковых нагрузках (например, массовая диспансеризация) система не справляется, так как:
- DWH имеет ограниченные ресурсы
- Camel работает в single-instance режиме
- Нет механизма балансировки нагрузки

**Как событийный подход решает проблему:**

| Характеристика | Apache Kafka | Текущее решение |
|---------------|--------------|-----------------|
| Горизонтальное масштабирование | Partition-based | Вертикальное (ограничено) |
| Пропускная способность | До миллионов msg/sec | Тысячи msg/sec |
| Хранение сообщений | Retention policies | Не предусмотрено |
| Балансировка | Consumer groups | Отсутствует |

**Пример масштабирования:**
```yaml
# Конфигурация Kafka для пиковых нагрузок
kafka:
  partitions: 100  # Параллельная обработка
  replication: 3   # Отказоустойчивость
  retention: 7d     # Хранение сообщений для replay
  
# Масштабирование потребителей
consumer-groups:
  ai-analysis:
    instances: 10  # 10 параллельных обработчиков
  reporting:
    instances: 5
```

### 3. Скорость реакции системы (Real-Time / Near-Real-Time)

**Проблема в текущей архитектуре:**
- BATCH-обработка с интервалом в часы/дни
- Невозможность получения актуальных данных
- Задержки в принятии решений

**Как событийный подход решает проблему:**

| Метрика | Текущая (DWH) | Целевая (EDA) |
|---------|---------------|---------------|
| Задержка данных | Часы | Секунды |
| Аналитика | BATCH | Streaming |
| Оповещения | Суточные отчёты | Мгновенные |
| Реакция на события | Ручная | Автоматическая |

**Примеры событий в реальном времени:**

> // Мгновенная реакция на завершение исследования
>
> StudyCompleted → AI Analysis Requested → PredictionGenerated → DoctorNotified
>
> // Всё это происходит автоматически, без ручного вмешательства!

> // Мгновенное обновление баланса
> 
> PaymentCompleted → Account Balance Updated → Customer Notification Sent
>
>// Клиент видит актуальный баланс сразу после платежа


### 4. Независимость команд (Team Autonomy)

**Проблема в текущей архитектуре:**
- Команды вынуждены координироваться через общий DWH
- Изменения в схеме требуют согласования
- Зависимость от команды DWH как от «узкого места»

**Как событийный подход решает проблему:**

| Принцип DDD | Реализация |
|-------------|------------|
| Domain Ownership | Каждый домен полностью владеет своими данными |
| Bounded Context | Чёткие границы ответственности |
| Ubiquitous Language | Общий язык внутри домена, API - наружу |
| Event Contract | Контракты событий - единственная зависимость |

**Команды могут работать независимо:**

Команда Медицины:
- Разрабатывает Patient Service
- Публикует события PatientRegistered, StudyCompleted
- Не зависит от других команд

Команда Финтека:
- Разрабатывает Banking Service
- Подписывается на PatientRegistered
- Создаёт счета для новых пациентов
- Не требует согласования с командой Медицины!


### 5. Устойчивость к ошибкам (Resilience)

**Проблема в текущей архитектуре:**
- Отказ DWH парализует все системы
- Нет механизма повторной обработки
- Потеря сообщений в Camel при сбоях

**Как событийный подход решает проблему:**

| Механизм | Описание |
|----------|----------|
| Event Retention | Сообщения хранятся и могут быть воспроизведены |
| Dead Letter Queue | Сбойные сообщения изолируются для анализа |
| Idempotency | Повторная обработка не вызывает дубликатов |
| Retry with Backoff | Автоматические повторные попытки |
| Circuit Breaker | Защита от каскадных сбоев |

## Сравнение архитектур

### Комплексное сравнение

| Критерий | Camel + DWH | Event-Driven (Kafka) | Победитель |
|----------|-------------|---------------------|------------|
| **Гибкость интеграции** | Низкая (транзитивные зависимости) | Высокая (децентрализованная) | EDA |
| **Масштабируемость** | Ограниченная | Практически неограниченная | EDA |
| **Latency (задержка)** | Минуты-часы | Миллисекунды-секунды | EDA |
| **Устойчивость к сбоям** | Низкая | Высокая | EDA |
| **Независимость команд** | Низкая | Высокая | EDA |
| **Сложность реализации** | Средняя | Средняя (требует экспертизы) | - |
| **Стоимость владения** | Высокая (лицензии, оборудование) | Оптимизируемая (облако) | EDA |
| **Time-to-Market** | Низкая | Высокая | EDA |

### Стоимостной анализ

**Текущие затраты:**
- SQL Server Enterprise Edition (дорогостоящие лицензии)
- Выделенные серверы для DWH
- Команда администраторов DWH
- Простои из-за медленных запросов

**Ожидаемые затраты с EDA:**
- Kafka (open-source) + облачная инфраструктура
- Горизонтальное масштабирование по требованию
- Сокращение команды DWH (миграция в домены)
- Быстрая окупаемость за счёт скорости разработки

## Риски и меры митигации

### 1. Сложность перехода

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Длительная миграция | Высокая | Высокое | Параллельный запуск, Strangler Fig Pattern |
| Потеря данных | Низкая | Критическое | CDC из DWH, валидация |
| Недостаток экспертизы | Средняя | Среднее | Обучение, привлечение консультантов |

### 2. Эксплуатационная сложность

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Сложность мониторинга | Средняя | Среднее | Готовые инструменты (Kafka Monitor, Prometheus) |
| Проблемы с порядком событий | Средняя | Среднее | Event ordering, saga pattern |
| Утечки данных | Низкая | Критическое | Шифрование, ACL |

## Дорожная карта внедрения

### Этап 1: Фундамент (0-6 месяцев)

```
1. Развёртывание Kafka-кластера
2. Пилот в одном домене (Финтех)
3. CDC из DWH в Kafka (Debezium)
4. Базовая система мониторинга
5. Определение контрактов событий
```

### Этап 2: Масштабирование (6-18 месяцев)

```
1. Подключение Медицинского домена
2. Подключение ИИ-сервисов
3. Внедрение ACL для интеграции с Camel
4. Потоковые витрины данных
5. Дополнительные потребители событий
```

### Этап 3: Зрелость (18-36 месяцев)

```
1. Отключение точек синхронной интеграции
2. Полный переход на события
3. Вывод DWH из эксплуатации
4. Мониторинг в реальном времени
5. Near-real-time аналитика
```

## Заключение

Переход на событийно-ориентированную архитектуру является стратегически обоснованным решением для компании «Будущее 2.0», потому что:

1. **Гибкость** — новые бизнес-направления интегрируются без изменения существующих систем
2. **Масштабируемость** — горизонтальное масштабирование под нагрузку
3. **Скорость** — переход от часов к секундам для аналитики и оповещений
4. **Автономия** — команды могут работать независимо
5. **Устойчивость** — механизмы обработки сбоев и replay

Текущая архитектура на базе Camel + DWH может использоваться как «мост совместимости» на этапе миграции, но в долгосрочной перспективе (3 года) событийная платформа должна стать основой интеграционного ландшафта компании, как это определено в стратегических целях «Будущего 2.0».
